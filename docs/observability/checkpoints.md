# Intra-Node Checkpoints

How to show *progress within* a single node while an agent is working on it.

---

## What Are Progress Ticks?

A **progress tick** is a small filled/unfilled dot or checkbox shown in a row on a live node card. Each tick represents one named intermediate stop that the agent is expected to pass through while completing the node's work.

**Key properties:**
- They are **authored upfront** (not generated by the machine)
- They fill in **as the agent passes each stop** (confirmed by evaluator receipts)
- They represent *where the agent is in its journey*, not *whether the outcome was correct*
- There are **7–12 of them** — enough that a human watching can tell at a glance whether the agent is moving, stuck on a specific step, or nearly done

**The analogy:** A flight tracker showing "Departed → Cruising → Descending → Landed." Each stop is meaningful and human-readable. "0 of 2 done" is not a flight tracker — that's just departure and arrival with nothing in between.

---

## Two Levels of Review Gates — Don't Confuse Them

| Thing | What it is | Lives where |
|---|---|---|
| **`type: milestone` graph nodes** | Big review gates *between* capabilities in the DAG | Graph-level, stays as-is |
| **Intra-node checkpoints** | Progress ticks *within* a single capability card | On the card, during live work |

Milestone nodes don't change. This doc is only about what happens *inside* a capability node while it's being worked on.

---

## Why Not `acceptance_criteria`?

`acceptance_criteria` are outcome checks. They answer: **"Did it work?"**

Progress ticks answer: **"Where is it right now?"**

These are different questions and the data is designed for different audiences:

| | `acceptance_criteria` | `checkpoints:` |
|---|---|---|
| Written for | Evaluator (pass/fail) | Human watching live |
| Granularity | 2–4 per node | 7–12 per node |
| Fills when | Evaluator confirms outcome | Agent reaches the step |
| Mid-work signal | Almost none | High |
| Example | "Tests pass" | "Step 4: scaffolded route handler" |

A node might have 3 acceptance criteria and take 30 agent actions. You'd watch nothing happen for 10 minutes, then two dots fill at the very end. That is not progress visibility — it is a delayed success indicator. **`acceptance_criteria` is too coarse to be used as progress ticks.**

Droid missions have 7–12 stops because that granularity maps to meaningful intermediate states a human can read at a glance. We know Droid works. We use that pattern here.

---

## The Decision: `checkpoints:` YAML List

Progress ticks use a new `checkpoints:` field authored on each capability node. This requires authoring discipline but is the only approach that gives genuine live progress signal.

**Example node YAML:**
```yaml
id: cap-auth-login
title: Implement login flow
acceptance_criteria:
  - ac-1: User can log in with email/password
  - ac-2: Invalid credentials show an error
  - ac-3: Session persists on refresh
checkpoints:
  - cp-1: Read existing auth module and map current session handling
  - cp-2: Design new login route contract (input/output shape)
  - cp-3: Scaffold route handler with placeholder response
  - cp-4: Implement credential lookup against user store
  - cp-5: Add bcrypt comparison and error path
  - cp-6: Wire session token generation
  - cp-7: Write unit test for valid login
  - cp-8: Write unit test for invalid credentials
  - cp-9: Write unit test for session persistence
  - cp-10: Run evaluator — confirm all acceptance criteria met
```

The `checkpoints:` list is a **narrative of the expected work**, written in the order the agent should do it. Each one is a human-readable sentence, not a test assertion.

## Rendering the Tick Row

```tsx
// Inside GDDPNode, when activity is present and checkpoints are authored
{activity && checkpoints.length > 0 && (
  <div className="tick-row" aria-label={`${completedCount} of ${checkpoints.length} steps done`}>
    {checkpoints.map(cp => (
      <span
        key={cp.id}
        className={`tick ${completedCheckpoints.has(cp.id) ? 'filled' : 'empty'}`}
        title={cp.label}
      />
    ))}
  </div>
)}
```

The `completedCheckpoints` set is populated by evaluator receipt events from the SSE stream — same stream already used for the drill-in panel. When the agent emits a receipt for `cp-4`, that tick fills.

---

## Authoring Rules

1. **7–12 stops per node.** Fewer than 7 is too coarse. More than 12 is noise.
2. **Each stop is an action, not an outcome.** Write "Scaffold route handler" not "Route handler works."
3. **Order matters.** The ticks fill top-to-bottom. Write them in the order the agent does the work.
4. **Last checkpoint should touch the acceptance criteria.** The final stop is typically "Run evaluator" or "Confirm all criteria met."
5. **`acceptance_criteria` stays.** It's for the evaluator. `checkpoints:` is for the human watching. Both exist, for different purposes.

---

## What Ticks Are NOT

Ticks show movement *along* a node (progress through work). They are **not**:
- Particles flying through space (that's Dream RSI)
- A replacement for milestone review gates
- A signal that the agent is on a correct reasoning path (that's the evaluator drift badge)
- A replacement for `acceptance_criteria` (both exist, both serve different purposes)

The metaphor is a flight tracker, not a particle system.
